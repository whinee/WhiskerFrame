## 6. Comprehensive verification

After functional implementation and the documentation-completion pass, run a dedicated, evidence-based QA phase. Tests added during implementation must be retained and included.

Implement and execute the appropriate levels of verification:

- **Unit:** functions, modules, state transitions, validation, parsers, boundary conditions, and error paths.
- **Integration:** actual interactions among subsystems, services, persistence, hardware abstractions, and external dependencies.
- **Regression:** known defects and previously failing behavior.
- **End-to-end:** critical user workflows from entry point to observable result, including setup, normal operation, failure handling, restart/recovery, and teardown.
- **Stress and endurance:** sustained load, concurrency, repeated operations, memory/resource growth, timeouts, recovery, and bounded-resource behavior.
- **Security:** authentication/authorization, privilege boundaries, input validation, secret handling, dependency risk, unsafe defaults, and relevant attack surfaces.
- **Performance:** meaningful baselines, critical-path timings, resource consumption, and regression detection.
- **Build/compatibility:** clean reproducible builds, packaging, supported configurations, migrations, target-platform constraints, and dependency installation.
- **Hardware-in-the-loop:** physical tests for behaviors that cannot be established by mocks or simulations, where hardware is available.

Use deterministic tests and appropriate test environments. Stress testing must use safe, realistic limits and must not endanger production data or hardware. Fix failures and rerun affected suites. Do not manufacture results, inflate counts, skip failures merely to meet the deadline, or describe an ATP plan as an executed test.

For each test suite, record the exact command, exit status, actual result, environment, and limitations. Clearly distinguish simulated, automated integration, hardware-in-the-loop, and manually observed evidence.
