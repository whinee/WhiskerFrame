## Hard requirement A — Mirror the actual physical screen

1. Inspect Git history, previous agent work, firmware, Pi daemon, serial protocol, framebuffer/grid representation, display commands, desktop viewer, and every preview recipe. Determine exactly where the physical screen's final pixels originate.
2. Explicitly distinguish:
   - **Mock/synthetic preview**: not acceptable as the requested mirror.
   - **Shared-renderer reconstruction**: acceptable only if it consumes the exact authoritative display state/commands used for the physical screen and proves parity; label it honestly.
   - **Actual physical capture**: a camera or hardware capture of the panel, if needed to prove the physical photons/pixels.
3. Establish whether the serial protocol carries enough information to reconstruct the screen. If it is write-only, do not pretend to read pixels back from the ILI9341. Instead, instrument the authoritative rendering/display-output path so the viewer receives the exact same ordered frame updates sent to the CYD, including clears, cursor, status bar, overlays, colors, geometry changes, and text. If that still cannot establish what is physically visible, explain the limitation and investigate a real camera/capture solution.
4. The viewer must continuously update as the actual device changes. Show unmistakable `LIVE DEVICE` versus `MOCK` status, the connected device, last frame/update time, and serial/link errors. Never silently fall back to mock mode. Mock mode must be explicitly requested and visually unmistakable.
5. Verify parity with a known sequence: clear screen, print distinctive text, scroll, change geometry, show status bar/cursor, trigger overlay, and update content. Capture the viewer output and the physical display using available evidence. Report which comparisons are exact and which are inferred.
6. PC keyboard input must reach the intended terminal through the documented bridge, preserve CardKB/Fn+Tab and terminal key semantics, avoid duplicate keystrokes, and bind control interfaces to localhost unless deliberately authenticated otherwise. Make viewer shutdown and reconnect behavior reliable.
7. Put user-facing viewer start/stop/status/diagnostic commands in the `justfile`. Fix the existing Tkinter deferred-exception `NameError` and all actual preview startup/update errors. Test the real command, not only `--mock`.

## Hard requirement B — Restore readable terminal typography

1. Recover the first known-good font and renderer from Git history/assets if possible. Compare the working reboot splash path with the broken normal terminal path.
2. Trace glyph assets all the way through firmware build inputs, generated headers, deployed firmware, Python renderer, terminal cells, status bar, cursor, and preview. Identify which code actually draws each kind of text. Verify what firmware is running; `just apply` may deploy/restart Python only.
3. Prefer the original good bitmap renderer or real 5×7 bitmap glyphs if appropriate. GNU Unifont is an alternative only if its actual rendered output is inspected and judged readable. Do not merely rename assets, change metadata, or regenerate headers without proving the physical device uses them.
4. Use one authoritative definition for glyph bitmap, row stride, advance, cell width/height, baseline, and scaling. Keep terminal wrapping/reflow consistent. Avoid overlap, thin outline-like glyphs, inconsistent spacing, clipped baselines, and distortion. Preserve RGB565, terminal-cell semantics, Unicode/box-drawing behavior, and memory constraints.
5. Generate and inspect side-by-side native-resolution (320×240) visual artifacts for the same strings in splash, terminal, desktop mirror, and every supported geometry (53×30, 40×20, 26×15, 17×10). Include a glyph sheet and representative punctuation, digits, `WhiskerFrame`, `Hello World!`, and `brb :3`. Tests alone cannot pass visual acceptance.
