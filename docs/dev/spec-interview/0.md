# WhiskerFrame / Cyberdeck: Requirements Interview

Purpose: turn "I have no idea what to write in the spec" into a real product requirements layer on top of the existing infra-heavy master specification. Suggested location in the repo: `docs/dev/spec-interview.md`.

---

## 0. Agent protocol (READ FIRST)

You are the orchestrator (`.agents/rules/orchestrator.md`). You are interviewing the developer. Follow these rules exactly.

1. **Write-ahead logging.** Per `.agents/rules/document-architecture-sync.md`: log each batch of questions to `docs/dev/ai-agent-handoff.md` as an OPEN Q BEFORE asking in chat. Log each answer verbatim IMMEDIATELY on receipt, BEFORE replying. On startup, read the journal and skip every ANSWERED question.
2. **Batches, not walls.** Ask 5 to 8 questions at a time, from ONE section, in ID order. Do not dump this file into chat. Start with Section A (tension flags), then follow the developer's energy; sections are independent.
3. **Never invent answers.** Answers of `idk` become OPEN DECISIONS: present 2 to 3 options with tradeoffs and a recommendation, then wait. `skip` means defer and re-surface later. `n/a` is final.
4. **Challenge vague answers.** "Fast", "light", "long battery" are not requirements. Ask for a number, a unit, or a test ("how would we know it works?"). One follow-up per vague answer, no more.
5. **Reality-check wishes against physics.** When an answer collides with the hardware (UART bandwidth, 416 MB RAM, USB 2.0 throughput, 3S pack energy, single Wi-Fi radio), say so with the arithmetic and offer alternatives. Do not silently accept an impossible requirement and do not silently drop it.
6. **Flag contradictions** between answers, and between answers and the existing spec (`docs/specifications/README.md`) or decisions (`docs/dev/ai-decisions.md`). Cite both sides.
7. **After each section**, synthesize requirements into `docs/specifications/product-requirements.md` as `REQ-<area>-<nn>` entries: priority (MUST / SHOULD / MAY / WON'T), the developer's rationale in their own words, a verification method, and the source answer ID(s). Then sync the Documentation Triad (DEC for any decision, spec for the contract, changelog for the history). Commit via the safe-autocommit policy.
8. **Keep the developer's voice.** Quote their words for motivation and intent. Keep the technical translation separate.
9. **No secrets** in answers or logs. Public info only. If a secret appears in chat, log "[secret received, redacted]".
10. **Do not end silently.** After each batch: state what was captured, what is now OPEN, and what you will ask next. Offer to stop for the day.

## How to answer (developer)

- Short is fine. Numbers and units are gold. Rough guesses are fine, say "~".
- `idk` = you propose options. `skip` = ask me later. `n/a` = doesn't apply.
- Answer in any order. Contradicting yourself later is allowed, just say "changed my mind".
- If a wish is physically impossible, the agent will say so, that's a feature.

> A: Text only currently. No current plans of adding GUI or adding trackball/joystick.

> A: RPI Zero 2W -> USB OTG Adapter -> USB Hub -> USB to SATA Caddy -> SATA SSD. It is currently not temporary. Scrap plans of adding USB 3 mux; too complicated.

- **A.06** Mobile data: the BOM lists no-name MSM8916 4G dongles (UZ801-style) as candidates; an earlier plan settled on a Huawei E3372h + DITO SIM. Which is current? MSM8916 sticks are tiny Linux computers with their own Wi-Fi: modem only, or a second compute node?
